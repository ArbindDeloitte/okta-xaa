Agent-to-agent (A2A): implementation & setup guide

Two ways for an agent in this project to call another agent instead of a portal or tool server: direct (packages/agent speaks the real A2A wire protocol, secured by the same Okta XAA mechanism already in xaa.ts) and via the Okta MCP Bridge (packages/agent-bridge would let the Bridge broker the call, the same way it already brokers MCP). Both needed one new agent to call — this project built that agent (HPE HR Agent, packages/agent-hr) and both call paths into it.

Summary

  • packages/agent-hr (port 3400): a small LLM-backed agent over a toy in-memory HR dataset, reachable over the real A2A protocol (@a2a-js/sdk), not MCP. It never talks to Okta itself — it only verifies bearer tokens.
  • Direct path: packages/agent/src/a2a.ts, structured like xaa.ts, does the same two-step Okta exchange (org AS token-exchange → ID-JAG → target's custom AS jwt-bearer), then calls message/send on the HR Agent with the resulting token. Surfaced to the model as one local tool, ask_hr_agent, alongside the existing MCP tools. The UI visibly distinguishes A2A tool calls from MCP ones (a colored badge/border in the trace log) so a viewer can tell the two governance stories apart at a glance.
  • Bridge path: fully specified and partially wired on the Okta/Bridge side, but not implemented in code — the Bridge's adapter cannot currently route the connection type this requires.
  • One new Okta object: HPE HR Agent, registered as a second AI Agent with its own Okta-native custom authorization server. No new registration for the direct-path caller — the existing Retail Ops Agent identity is reused, with one new resource connection pointed at the HR Agent.

1What A2A is, and how it differs from MCP

MCP connects an agent to tools and data: a fixed, structured, schema-typed function list the server defines and the client calls deterministically — everything else in this repo (the Retail Portal MCP server, the Bridge's virtual MCP endpoint) is this shape. A2A (Agent2Agent protocol) connects an agent to another agent: the message you send is a free-text task, not a function call, and the thing answering can reason, decide it needs more information, run its own tools internally, or take a while — the protocol has task states for that (submitted, working, input-required, completed, failed, …). The two are complementary, not competing: an A2A agent is free to be an MCP client internally (ours is not, by design — §4).

  • Every A2A server publishes an Agent Card, a JSON document at /.well-known/agent-card.json, describing its name, description, where to reach it (supportedInterfaces[].url in the SDK version used here, not a top-level url), and the "skills" it exposes.
  • The primary operation is the JSON-RPC 2.0 method message/send: POST a Message (a role plus one or more parts, typically a text part) and get back either an immediate Message reply or a Task. This project uses message/send only — it fits the existing synchronous tool-call loop in agent.ts with no restructuring.
  • SDK used: @a2a-js/sdk v1.3.0. Server side: DefaultRequestHandler, InMemoryTaskStore, an AgentExecutor you implement, mounted behind Express via agentCardHandler/jsonRpcHandler (@a2a-js/sdk/server/express). Client side: ClientFactory, JsonRpcTransportFactory, DefaultAgentCardResolver, createAuthenticatingFetchWithRetry. Auth hook: a UserBuilder — (req) => Promise<User> — is where this project's bearer-token verification plugs in (packages/agent-hr/src/auth.ts).

2How Okta secures agent-to-agent calls

Console name: "Connect to another AI Agent", connection type "Cross App Access (Agent-to-agent)" (internal identifier IDENTITY_ASSERTION_A2A_SERVER — this exact string is also what the Bridge's own console shows when it cannot route a connection of this type; see §6).

The mechanics are the same two-step exchange xaa.ts already implements for ordinary XAA, just retargeted — with two corrections versus the original plan, both confirmed live against real Okta and real errors.

Step 1 — token exchange at Okta's org authorization server (RFC 8693)

That produced invalid_target: Token Exchange requests must include a valid audience of the authorization server. Setting resource equal to audience is the confirmed working shape, per Okta's own System Log.

Response: an ID-JAG, 5 minutes, single-use — identical shape to the one retail-auth already validates.

Step 2 — JWT Bearer grant at the target's own custom authorization server (RFC 7523)

grant_type = urn:ietf:params:oauth:grant-type:jwt-bearer, assertion = the ID-JAG, at https://{yourOktaDomain}/oauth2/{authServerId}/v1/token — an Okta-hosted custom AS object (an aus… id), not a hand-built server like retail-auth.

Confirmed gotcha — Access Policy client assignment. The target AS's Access Policy has its own "Assigned to clients" scoping, separate from the delegation link itself. A delegation can succeed at the org-AS step (you get a valid ID-JAG) and still fail here with no_matching_policy → access_denied if the calling client isn't on the policy's allowed-clients list. This bit twice during this build. Every new caller needs to be added to this list explicitly — it is not automatic, even once the delegation shows as connected. Diagnosable via Okta's System Log: LegacyEventType app.oauth2.as.token.grant_failure, DebugData fields AuthorizationServerAudience / ResourceType (A2A_RESOURCE_URL / STATIC_AS_AUDIENCE).

Access token audience: the minted token's aud claim, observed live, did not unambiguously confirm whether Okta carries the resource parameter through to the final token or instead stamps the custom AS's own statically-configured "Default Audience" — this did not need resolving: packages/agent-hr/src/auth.ts accepts either value (HR_AGENT_URL / the Default Audience, or the AS's own issuer URL) as valid.

Setup — confirmed

  • Both sides must be registered AI Agents in the Okta directory — the resource picker in "Connect to another AI Agent" only lists AI agents, not plain Applications.
  • The target's custom AS must define the custom scopes (hr:read, hr:write), and its Access Policy must allow the JWT Bearer grant type and list the calling client (see the gotcha above).
  • Okta's own wizard configures both the caller and the resource side in one step. The audience/resource URL it captures locks in for every future delegation to that same resource — get it right the first time (the exact value you intend to put in .env as HR_AGENT_URL/the AS's Default Audience, not a placeholder).
  • Each registered AI agent gets its own OIDC app + key pair at registration. The HR Agent only ever receives calls, so it never needed that key for anything our own code does.

A second, separate thing shares the word "A2A": the MCP Bridge's own Resource type (the "Create resource" dialog, Type = A2A) — the Bridge product's own resource catalog entry, used for its own proxying model (§6). Both are needed together for the Bridge path in principle: the Okta-native delegation governs authorization, the Bridge's Resource + Managed Connection governs HTTP routing. As §6 found, the routing half isn't implemented yet. One UI note: the "Create resource" dialog's "MCP Protocol Version" field is a leftover from a form shared with MCP resources — it does not apply when Type is A2A; leave it blank.

3Architecture: one new agent, two call paths

┌─────────────────────────────────────────────┐ │ HPE HR Agent (packages/agent-hr, :3400) │ │ @a2a-js/sdk server + its own small LLM │ │ loop over a toy in-memory HR dataset │ │ verifies Bearer tokens; never calls Okta │ └───────────────▲───────────────▲─────────────┘ │ │ DIRECT A2A ✅ working │ │ VIA BRIDGE ⛔ blocked by the Bridge's adapter Retail Ops Agent (packages/agent, :3000) │ │ HPE Ops Agent (Bridge) (packages/agent-bridge, :3300) ├─ reuses this user's ID token │ ├─ would reuse its existing Bridge OAuth session token ├─ Okta org AS: token-exchange → ID-JAG │ ├─ Okta MCP Bridge: Resource "HPE HR Agent" (type A2A) ├─ HR Agent's custom AS: jwt-bearer → HR access token │ + Managed Connection — both configured successfully └─ message/send (A2A), Bearer HR access token ─────────┘ └─ but the Bridge adapter refuses to route this connection type — nothing calls through it

Both callers expose (or would expose) the same thing to the model: a local tool ask_hr_agent(task: string). The model decides when a question needs the HR Agent and calls it like any other tool; only the plumbing underneath differs by app. Only the direct path's tool is actually wired up and callable today.

4The new component: HPE HR Agent (packages/agent-hr)

A deliberately small LLM-backed agent, not just a deterministic function server — that distinction is the whole point of an A2A demo instead of one more MCP server. Port 3400 (3000 / 3200 / 3300 / 3400).

  • Data (src/data.ts): 5 fictional employees (name, title, department, manager, email, PTO balance) in a mutable in-memory array.
  • Skills (src/skills.ts): lookup_employee (scope hr:read) and update_pto_request (scope hr:write) — a read scope and a write scope, exactly as the retail scopes already demonstrate. Each skill's required scope is enforced against the verified caller's granted scopes before the skill runs.
  • Its own small LLM loop (src/llm.ts): receives the free-text task, runs one bounded round of Claude tool-use against the two skills, then a final text turn — no open-ended agentic loop. Reuses the same Bedrock/ANTHROPIC_BASE_URL wiring style as packages/agent/src/config.ts, including the AWS_BEARER_TOKEN_BEDROCK → BEDROCK_API_KEY fallback mapping (this agent runs as its own process with its own config, so that mapping had to be copied here too — missing it caused a confusing "ANTHROPIC_API_KEY (or BEDROCK_API_KEY) is not set" error even once Okta auth was already passing).
  • Agent Card (src/card.ts) at /.well-known/agent-card.json: name "HPE HR Agent", supportedInterfaces[0].url pointing at HR_AGENT_URL, Bearer security scheme, the two skills with per-skill security requirements.
  • Token verification (src/auth.ts): createRemoteJWKSet + jwtVerify against HR_AGENT_AUTH_ISSUER, accepting either HR_AGENT_URL or HR_AGENT_AUTH_ISSUER as a valid aud (§2). No session, no sign-in page, no cookies. On a verification failure it still decodes (without verifying) and logs the claims plus the expected audiences, so a bad token's actual shape is visible without turning on HR_AGENT_LOG_CLAIMS.
  • Demo HR portal (public/index.html, served at /portal): a presentable, auto-refreshing read/write view of the same in-memory data the agent reads and writes — a live PTO approval made through chat shows up here within ~2 seconds, no refresh needed. Supports inline edit, quick +/- PTO adjustment, and adding new demo records. Loopback-only unless HR_PORTAL_PUBLIC=true (same default pattern as packages/retail-portal's own admin console).
A dev tunnel forwards through a local process that still looks like loopback traffic to Express, so the portal's loopback guard does not meaningfully block tunnel-forwarded requests — low risk given an unguessable tunnel URL, but worth knowing if HR_AGENT_URL is ever pointed at a public tunnel.

5Path 1 — direct A2A in packages/agent built, working

packages/agent/src/a2a.ts, structured like xaa.ts:

  • Reuses oktaClientAuth() from xaa.ts unchanged — same Okta org, same existing agent registration. No new Okta AI Agent was needed for this caller; only the HR Agent side is new.
  • performA2aExchange(tokens, trace) does the two-step exchange from §2 (the corrected resource = audience shape, the id_token subject type), with the same scope-narrowing retry on invalid_scope that performXaa already uses, returning { accessToken, scope, expiresAt }. Appends the same kind of human-readable TraceSteps the existing governance panel already renders.
  • callAgentOverA2a(baseUrl, task, getToken): caches only the Agent Card per base URL (never a Client), builds a fresh authenticated fetch + ClientFactory + Client per call, so tokens never cross-contaminate between calls or sessions.

Integration into the existing chat loop (agent.ts): one new local tool, ask_hr_agent, offered to the model alongside the MCP tools whenever an askHrAgent callback is supplied — both the Groq and Anthropic tool-building paths support it. callTool special-cases this name before the MCP branch. Everything else in runAgent — the tool-round loop, the trace, the UI — is unchanged.

Session wiring (index.ts): ensureHrAccess(req, trace) caches the HR access token on req.session.hr, reusing the session's ID token (never the refresh token — Okta doesn't rotate it). A shared withRefreshLock(sessionID, fn) mutex serializes this alongside the retail exchange, since both touch the same session tokens. POST /api/hr/connect mirrors /api/xaa/connect; /api/me and every /api/chat response include the HR Agent's granted scope and expiry.

UI: a new "HR Agent (A2A)" card next to the Cross App Access card, showing granted scopes and a manual "Run HR Agent exchange" button. In the tool-call trace log, A2A calls get a distinct colored left border and an A2A badge (vs. an MCP badge on ordinary tool calls) so a viewer can tell the two protocols apart at a glance — added specifically so a client audience can see the governance difference, not just read about it.

6Path 2 — via the Okta MCP Bridge confirmed blocked

The Bridge already proxies MCP: it resolves a URL on its own domain and the agent's MCP client connects to that, not the portal's real URL — the Bridge is a full terminating proxy that does the Okta exchange, then relays to the real server. The original plan expected the same shape to hold for A2A. It does not, today.

What was configured, and worked

  1. Bridge Resource. Resources → Create resource, Type A2A, Name hr-system, URL = the HR Agent's own base URL (a dev tunnel was used so the Bridge's remote infrastructure could reach a locally-running agent — the same reason retail-auth/ retail-portal already use tunnels rather than localhost).
  2. Managed Connection. On the Bridge's own AI Agent's detail page → Resource connections → Add resource connection → Connect to another AI agent → select HPE HR Agent. This single flow auto-filled the Authorization server and Audience/resource URL from the already-registered HPE HR Agent AS (confirming the audience=resource=issuer shape from §2 holds for any caller), and after picking scopes and saving, Okta confirmed both "Delegation ✓" and "Resource connection ✓" in one step.

Where it stops

The Bridge's own Connections & Resources list shows this new connection tagged A2A Server / INCLUDE_ONLY, with the correct scopes — but with an explicit warning, quoted verbatim:

From the Bridge's own admin console:
Connection type IDENTITY_ASSERTION_A2A_SERVER is not currently supported by this adapter. Routing through this connection is disabled.

Compare this to the existing, working MCP connection shown in the same list ("HPE order portal Bridge"), which has a real backing resource entry (hpe-order-portal-mcp-v4, a concrete URL, Auth: okta-cross-app) that the adapter can route through. The HR Agent's A2A connection has no equivalent backing route — confirming this is a Bridge product/adapter limitation, not a misconfiguration: Okta's core platform fully supports Agent-to-Agent delegation (proven by the direct path), but the Bridge's HTTP-routing layer hasn't been built out to act on connections of this type.

Consequence for this project: no a2aCandidates()/resolveA2aUrl() discovery code, and no ask_hr_agent tool, were written in packages/agent-bridge. Writing speculative candidate-URL-probing code would be pointless — there is nothing to find, since routing through this connection type is explicitly disabled at the platform level, not merely undocumented.

If Okta ships adapter support for this connection type later: the Okta-side configuration above should carry over unchanged. Revisit this section, build a2aCandidates()/resolveA2aUrl() next to the existing mcpCandidates()/resolveMcpUrl() in packages/agent-bridge/src/index.ts (probing via a GET to <candidate>/.well-known/agent-card.json, as tryInitialize() already does for MCP), reuse callAgentOverA2a() from packages/agent/src/a2a.ts for the actual call, and write scripts/e2e-a2a-bridge.ts only once the Bridge's real proxy URL shape is empirically known.

Housekeeping, not required: since routing is disabled, there's no functional reason to keep HR_AGENT_URL pointed at a dev tunnel rather than http://localhost:3400 for ongoing direct-path use — the tunnel only mattered for the Bridge's (currently nonfunctional) attempt to reach the agent. Safe to leave in place or revert; a cleanup preference, not a correctness issue.

7Okta console setup (as actually done)

A. Register the new AI agent

  1. Directory → AI Agents → Register AI Agent. Name it HPE HR Agent. Allow users to access this agent → create a new linked OIDC app.
  2. Activate it, same steps as the existing agent's setup in OKTA_SETUP.html (its §1) — assign it to the same test user(s).

B. Its custom authorization server (Okta-native)

  1. Security → API → Authorization Servers → Add Authorization Server. Name it (e.g. "HPE HR Agent AS"), set an Audience (this becomes HR_AGENT_URL, e.g. http://localhost:3400).
  2. Scopes: add hr:read and hr:write.
  3. Access policy: add a rule allowing the JWT Bearer grant type. Assigned to clients: explicitly add every caller here — this does not happen automatically just because a delegation link exists (§2's confirmed gotcha).
  4. Note its Issuer URL → this becomes HR_AGENT_AUTH_ISSUER.

C. Wire the delegation for the direct path ("Connect to another AI Agent")

  1. Caller = Retail Ops Agent. Resource (AI agent) = HPE HR Agent.
  2. Authorization server = the one just created. Audience/resource URL = the AS's own issuer URL (the step 1 audience = resource value from §2 — not HR_AGENT_URL as a separate field).
  3. Select scopes hr:read, hr:write.
  4. Confirm the caller's client id is on the Access Policy's client list (step B.3) — if the Okta System Log later shows no_matching_policy for this caller, check this first.

D. Bridge path — configured, confirmed blocked see §6

  1. Bridge console → Resources → Create resource: Type A2A, URL = the HR Agent's reachable base URL.
  2. Bridge console → the Bridge's own AI Agent → Resource connections → Add resource connection → Connect to another AI agent → HPE HR Agent → select scopes → save.
  3. Same Access Policy client-list check as C.4, for the Bridge agent's own client id.
  4. Result: the connection appears, correctly scoped, but tagged with the adapter's routing-disabled warning. No further Okta-side action resolves this.

Appendix — the alternative not taken

Instead of an Okta-native custom AS, the HR Agent could run its own bespoke Express OAuth server, exactly mirroring packages/retail-auth (its own signing key, its own handleJwtBearer, its own ALLOWED_SCOPES). This is strictly more code, and buys back the "resource owner runs its own, non-Okta-hosted AS" story the original XAA pattern already tells once. The Okta-native route tells a different, equally real story — "two first-class Okta AI Agents talking to each other with nothing custom in between" — the more interesting one for an agent-to-agent demo, and the one this project built.

9Security & governance notes

  • The ID-JAG is single-use and short-lived (5 minutes) — unchanged versus ordinary XAA; Okta enforces this itself for an Okta-native custom AS.
  • Scopes are the only access control on the HR Agent — no per-user role layer like the portal's PORTAL_USER_ROLES. Narrowing the resource connection's scopes is what changes what the model can ask the HR Agent to do; demonstrated live (granting only hr:read correctly blocks update_pto_request).
  • hr:write is the scope worth demonstrating being revoked live, the same way orders:write/returns:write already are for the portal.
  • Anything the HR Agent returns is treated as untrusted input to the calling agent's own LLM turn, same as any MCP tool result already is in agent.ts.
  • Token logging is opt-in and off by default (HR_AGENT_LOG_CLAIMS), matching the OBO_LOG_TOKEN pattern elsewhere — claims only, never the raw token; the failure path logs decoded claims too (without verifying) so a bad token's shape is diagnosable without turning this on.
  • The HR portal's loopback guard does not meaningfully stop tunnel-forwarded traffic (§4) — low risk given an unguessable tunnel URL, but not a hard boundary if HR_AGENT_URL is ever pointed at a public tunnel for an extended period.

10Testing

scripts/e2e-a2a.ts, following scripts/e2e-obo.ts's shape: a mock Okta server in-process serving both the org-AS token-exchange endpoint and the HR Agent's own AS (JWT-bearer + JWKS), the real agent-hr process spawned and exercised over real HTTP, packages/agent's own a2a.ts/agent.ts imported in-process, a mock LLM, and a mock MCP server. Sections covered: config validation; the happy path; scope narrowing to hr:read only; Okta's own scope-narrowing retry; replay/audience/resource attacks against the HR Agent's AS; the HR Agent itself rejecting bad bearer tokens (empty, expired, wrong-audience); a full chat loop exercising ask_hr_agent through a mock outer LLM; and the tool correctly absent when no askHrAgent callback is supplied. Runs hermetically by default and also with E2E_LIVE_LLM=1 against the real configured LLM provider. npm run test:a2a.

No Bridge-path e2e test exists or is planned, per §6.
