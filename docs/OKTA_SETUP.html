Okta setup: step by step

Configure Okta Cross App Access (XAA) so the Retail Ops Agent can reach the Retail Portal, centrally governed by Okta. Based on Okta's AI agent-to-app help pages. Menu names can change between Okta releases; if a label differs, go by the intent.

Before you start

You need:

  • An Okta org with the Single Sign-On product.
  • An admin account that can manage AI agents.
  • At least one test user.
  • An Anthropic API key (for the agent's LLM).
Okta limits XAA under SSO to 250 ID-JAG tokens per user, per resource app, per month. Each time the agent uses the exchange it consumes one.

1Create the AI agent (the requesting app)

The agent is what users sign in to, and what asks Okta for permission to call the portal.

  1. Register the agent. Admin Console → Directory → AI Agents → Register AI Agent.
  2. Profile. Name it Retail Ops Agent, add a description (optional), click Next.
    • The Identifier section (Platform / External ID) is "recommended if available". It is for matching agents built on a listed agent-builder platform, so leave both blank for this custom agent.
  3. User access and authentication → Allow users to access this agent: choose Create a new OIDC app linked to this AI agent, then Next.
    • This permanently links the agent to that app. To change it later you must delete and recreate the agent.
    • The agent is created with status STAGED.
  4. Register the agent's public key — do this before editing the app, or Okta refuses to save it with 'jwks' is required when 'token_endpoint_auth_method' is 'private_key_jwt'.
    • In the project folder run npm run gen:key (first time) or npm run show:key (to re-print it). Copy the printed public JWK.
    • On the AI agent → Client registration tab → Configure next to Public/private key → Add public key → paste the JWK → Done.
    • Click Activate, then Enable in the dialog.
    • Okta may show its own KID for the key, different from the one in the JWK. That's fine: if the KIDs differ, set AGENT_KEY_ID=<the KID shown in Okta> in .env.
    • Copy the Client ID (also on the linked app → General → Client Credentials, where Client authentication shows Public key / Private key, which is what we want).
  5. Configure the linked OIDC app. Applications and Resources → Applications → the linked app → General → Edit. If the wizard didn't already ask, set:
    • Grant types: Authorization Code and Refresh Token (under Core grants). The refresh token is what the agent exchanges for the ID-JAG.
    • Refresh token behavior: either Use persistent token or Rotate token after every use works. With rotation, the agent keeps the new refresh token that Okta returns and runs one exchange at a time per user session. If Okta ever answers invalid_grant, sign in again.
    • Sign-in redirect URI: http://localhost:3000/callback
    • Sign-out redirect URI (optional): http://localhost:3000/
    • PKCE ("Require PKCE as additional verification") can stay off; the agent always sends PKCE anyway.
  6. Assign users. AI agent → User access tab → Application → Assignments → assign your test user or group.
    • The linked app starts inactive, so it may show under the Inactive tab.
  7. Activate the agent. On the AI agent page: Actions → Activate.
You now have: OKTA_ISSUER, AGENT_CLIENT_ID, and the key in .keys/ (AGENT_AUTH_METHOD=private_key_jwt). No client secret is needed.

2Create the Retail Portal app (the resource app) and enable XAA

This tells Okta that the Retail Portal can be called by agents, and which scopes exist.

  1. Create the app. Applications and Resources → Applications → Create App Integration → OIDC - Web Application (a custom OIDC app supports XAA).
    • Name: Retail Portal. Any placeholder redirect URI works, e.g. http://localhost:3101/callback.
    • Choose Skip group assignments for now, then Save.
  2. Open the XAA settings. Retail Portal → Machine Assignments tab → Callers tile → Edit next to Cross App Access (XAA) → Enable.
  3. Fill in the fields:
    • Issuer URL: http://localhost:5101. The base URL of the resource authorization server, which here is the retail-auth service.
    • Audience/tenant ID: optional; leave empty (only for multi-tenant servers).
    • Scopes: add the 7 scopes above, one per field (use + Add for more).
  4. Click Save.

3Connect the agent to the Retail Portal

This is the central policy: which agent may reach which app, with which scopes.

  1. Directory → AI Agents → Retail Ops Agent → Resource connections tab → Add resource connection.
  2. Application → Application instance: select Retail Portal, then Enable.
  3. Fill in:
    • Resource indicator: http://localhost:3101
    • AI agent's client ID registered in this app: agent-at-retail
    • Scopes: Allow any scope, or Allow specific scopes. To try governance, pick only products:read orders:read.
  4. Click Add.
This is the screen an admin uses to narrow or revoke the agent later. Change the scopes or disable the connection and the agent's tool list changes on its next exchange.

4Configure the project

  1. Create your .env from the template (PowerShell): 
    copy .env.example .env
  2. Fill it in: 
    OKTA_ISSUER=https://<your-org>.oktapreview.com
AGENT_CLIENT_ID=<from Step 1>
AGENT_AUTH_METHOD=private_key_jwt               # key at .keys/agent-private.jwk.json
ANTHROPIC_API_KEY=<your key>

RETAIL_AUTH_ISSUER=http://localhost:5101        # = Step 2 Issuer URL
RETAIL_RESOURCE=http://localhost:3101           # = Step 3 Resource indicator
RETAIL_AGENT_CLIENT_ID=agent-at-retail          # = Step 3 client ID
RETAIL_AGENT_CLIENT_SECRET=<choose a secret>
  3. Install, check and start: 
    npm install
npm run check:env      # checks .env, the key, and that Okta accepts the agent's key
npm start

5Verify

  1. Open http://localhost:3000 → Sign in with Okta (as the assigned user).
  2. Click Run XAA exchange. Expect three green steps:
    • User session (refresh token + ID token)
    • Okta: refresh token → ID-JAG
    • Retail authorization server: ID-JAG → access token
  3. Expand step 2's claims. You should see header typ: oauth-id-jag+jwt, iss = your Okta org, aud = http://localhost:5101, client_id = agent-at-retail, and scope = what the connection allowed.
  4. Ask "Which orders are still processing?" Then open http://localhost:3101 → Audit log to see the call.
  5. Test central governance. In Step 3 change Scopes to specific ones, then click Run XAA exchange again. The MCP tools visible list should shrink.

If something fails

The agent's trace panel shows the failing step and Okta's error.

Trace showsCheck
Saving the linked app fails with 'jwks' is required when 'token_endpoint_auth_method' is 'private_key_jwt'The public key isn't registered yet: do Step 1.4 first, then save the app settings
Step 3: returned HTTP 404 (text/html) instead of OAuth metadata, or "Not Found" HTMLAnother program owns the auth server's port (common on Windows: a Python/Flask app on 5001 can share the port with Node, and localhost then reaches the wrong one). Change AUTH_PORT and RETAIL_AUTH_ISSUER to a free port (this project uses 5101), update Issuer URL in Okta (Step 2.3) to match, and restart. The auth server now warns at startup if the port is shared

Optional extras

Using a client secret instead (fallback)

Only if your app is set to Client secret (linked app → General → Client Credentials → Edit → Client secret): generate a secret under the agent's Client registration, then set AGENT_AUTH_METHOD=client_secret and AGENT_CLIENT_SECRET=... in .env.

Portal roles

The portal maps the ID-JAG's email claim, or else its sub (an Okta ID like 00u...), to a role. Find who the portal saw at http://localhost:3101 → Users & roles, then set for example:

PORTAL_USER_ROLES=alice@example.com=manager,00u1abcdEXAMPLE=viewer
PORTAL_DEFAULT_ROLE=support

Open questions

These couldn't be confirmed from Okta's docs.

Can Okta reach localhost? The help page says Okta "uses [the Issuer URL] for token verification requests". If Step 2 fails with target/audience errors even though the values match, localhost may be unreachable from Okta. Expose retail-auth through an HTTPS tunnel (ngrok, Cloudflare Tunnel), then use the tunnel URL for both the Step 2 Issuer URL and RETAIL_AUTH_ISSUER. The auth server also answers /.well-known/openid-configuration, in case Okta looks for that.
  • Which authorization server mints the ID-JAG isn't stated on the help pages. Okta's blog says the org authorization server, so OKTA_ISSUER is the plain org URL.
  • Whether email appears in the ID-JAG (use sub in PORTAL_USER_ROLES if not).
  • Whether the optional resource parameter is accepted: set XAA_SEND_RESOURCE=false to drop it.
